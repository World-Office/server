# P4-D02 — Rust: OMML math — m:oMath/m:oMathPara verbatim + linear text extraction, managed round-trip

Implements the PORT-PLAN Phase 4 math item: OMML (Office Math Markup
Language) objects — paragraph-level `m:oMath` (inline) and `m:oMathPara`
(display) wrappers — parse into a typed model that keeps the subtree
byte-verbatim and extracts the linear `m:t` text, and re-serialize unchanged,
so a parse → serialize → parse cycle keeps the math exactly where and as it
was.

## What landed

| piece | what it is |
|---|---|
| `model::DocxMath` | `{ verbatim, linear_text, display }` — the byte-exact source subtree (`m:oMath`, or the whole `m:oMathPara` wrapper including `m:oMathParaPr` for display math), every `m:t` chunk concatenated in document order, and the inline/display flag. |
| `DocxRun::math` | The math object a run carries. Paragraph-level math becomes a marker run (same pattern as bookmarks/sdt/revisions) so run order — and thus math position between its neighbor runs — round-trips; `run.text` carries the linear text so converters and renderers show it. Run-nested math (`m:oMath` inside `w:r` content, EG_RunInnerContent) is captured on its own run's `math` field without touching `run.text`. |
| parser (`parse_math`) | `parse_paragraph` routes `m:oMath`/`m:oMathPara` children (namespace `http://schemas.openxmlformats.org/officeDocument/2006/math`) to `parse_math`, which captures `node.range()` byte-exactly and collects `m:t` descendants; `parse_run` captures run-nested `m:oMath` the same way. |
| serializer | Pure math marker runs hoist out as the bare verbatim element (never wrapped in `<w:r>`; the linear extraction never re-emits as `w:t` — that would duplicate the math). Runs carrying nested math serialize through `serialize_run`, re-emitting the verbatim subtree inside their `<w:r>` (`is_math_marker_run` discriminates the two shapes). The document root now also declares `xmlns:m` so re-serialized documents stay namespace-well-formed. |
| `gap_docx_math_roundtrip` | converter_gaps gate: inline math between two text runs + a centered display fraction → verbatim equality, linear text (`Emc2=ahc`, `a+b2`), html rendering of both, byte-identical re-emission in position, no duplicated linear `w:t`, and re-parse equality. |
| `gap_docx_math_in_run_roundtrip` | Run-nested variant: `w:r/m:oMath` captures verbatim + linear text, re-emits inside its run, round-trips identically. |

## Deliberate non-changes

* **No OMML → LaTeX/MathML/OMML-layout conversion**: converters render the
  linear `m:t` text only; real math layout stays a renderer concern.
* **Math inside tables/headers** rides the same run/paragraph machinery and
  needs no special handling; `m:oMathPara` as a *block* outside `w:p` is not
  a thing in Word documents.
* **`m:oMath` nested in `w:r` with sibling `w:t`**: the verbatim re-emission
  preserves both, but relative order of `w:t` vs `m:oMath` inside the run is
  not guaranteed (same known limitation as the `w:pict` escape hatch).
* The typed model does not expose `m:rPr`/`m:sty` etc. — they live inside the
  verbatim capture.
